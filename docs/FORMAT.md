# Формат `.drp` — что известно и что нет

## Статус: КОНТЕЙНЕР ИЗМЕРЕН, СХЕМА — ЕЩЁ НЕТ

Отчёт Resolve Doctor с реальной машины (Windows 11, DaVinci Resolve 21.0.10011,
2026-08-05) дал первые факты о формате. Это измерения, а не догадки:

| Что | Значение |
| --- | --- |
| Контейнер | **ZIP** (`50 4b 03 04`) |
| Корневой элемент | `project.xml` |
| Медиапул | дерево `MediaPool/**/MpFolder.xml`, включая папку `000_Timelines` |
| Таймлайны | по одному файлу `SeqContainer/<uuid>.xml` |
| Кодировка | UTF-8; строк UTF-16-LE не встретилось |

Отсюда следует главное: **таймлайн клипа достижим.** Имя таймлайна и
расположение клипа лежат в XML внутри архива, а не в недоступном двоичном
формате.

Чего ещё нет: схемы этих XML — какие теги и атрибуты внутри `SeqContainer`
описывают дорожку, таймкод и ссылку на клип медиапула. Без неё парсер писать
нельзя, и он не написан.

Это собирает та же диагностика, версия 1.1: для каждого проекта она выгружает
список элементов архива и инвентарь XML — имена тегов, имена атрибутов и по
несколько примеров значений. Полные файлы проектов при этом никуда не уезжают.

### Побочный вывод: расширение .drp занято не только Resolve

Из 125 найденных файлов `.drp` проектами Resolve оказались около семидесяти.
Остальное — модели VideoProc Converter AI (сигнатура `DIGI`, до 100 МБ каждая) и
наборы ударных Reason. Поиск теперь распознаёт контейнер и пропускает чужие
файлы, но считает их и показывает отдельной строкой. Неопознанные форматы
по-прежнему сканируются: старая версия Resolve могла писать контейнер, которого
здесь никто не видел, и молча его выбросить — худшее, что можно сделать.

## Прежний статус: НЕ ПРОВЕРЕНО НА РЕАЛЬНЫХ ФАЙЛАХ

Приложение написано на машине, где **нет ни DaVinci Resolve, ни одного файла
`.drp`**. Проверено напрямую (macOS 27, Apple Silicon, 2026-08-05):

| Проверка | Как | Результат |
| --- | --- | --- |
| Resolve установлен | `ls /Applications`, `mdfind` | не найден |
| Каталог скриптинга | `/Library/Application Support/Blackmagic Design/...` | не найден |
| Файлы `.drp` на диске | `mdfind`, `find ~` | не найдено ни одного |

Поэтому в этом документе нет ни одного утверждения вида «в `.drp` лежит XML».
Формат проектов Resolve не документирован публично и менялся между версиями —
любое такое утверждение было бы догадкой, зашитой в код.

## Как приложение обходится без знания формата

Версия 1.0 не разбирает структуру. Она:

1. Читает первые 512 байт и определяет контейнер по сигнатуре:
   `PK\x03\x04` → ZIP, `\x1f\x8b` → gzip, `\x78 \x01|\x9c|\xda` → zlib,
   `SQLite format 3\x00` → SQLite, `<` → XML, `{`/`[` → JSON, иначе текст или
   двоичный.
2. Разворачивает контейнер в поток (или несколько потоков — по одному на элемент
   ZIP), при необходимости распаковывая вложенное сжатие до двух уровней.
3. Вытаскивает из потока все последовательности печатных символов и декодирует
   их как UTF-8, UTF-16-LE (в обоих выравниваниях) и — если запрос содержит
   не-ASCII — CP1251.
4. Ищет запрос в этих строках.

Такой поиск устойчив к смене формата: если Blackmagic завтра поменяет
контейнер, изменится максимум скорость, а не результат.

**Ключевое правило:** файл, который не удалось прочитать или распаковать,
помечается ошибкой и показывается отдельно. Он никогда не попадает в категорию
«совпадений нет». Для инструмента поиска молчаливый ноль — худший из возможных
отказов.

## Чего версия 1.0 принципиально не может

| Хочется | Почему нельзя сейчас |
| --- | --- |
| Показать таймлайн и таймкод клипа | Требует разбора структуры проекта. Структура неизвестна. |
| Отличить клип на таймлайне от клипа в медиапуле | То же. |
| Найти по Reel Name / Tape Name / Camera Roll отдельным полем | Поиск по строке найдёт значение, но не сможет сказать, что это было именно поле Reel Name. |
| Достать текст из Text+ | Неизвестно, хранится ли он в проекте в открытом виде. |
| Импортировать проект в Resolve | Требует скриптового API на живой установке. Пункт меню есть и выключен с объяснением. |

Ни одна из этих строк не «в разработке». Каждая станет возможной ровно тогда,
когда появятся факты о формате.

## Как эти факты собрать

На машине с реальными проектами:

```bash
rps-probe "J:\Проекты" --out drp_report.md --limit 10
```

Отчёт покажет по каждому файлу:

- первые 16 байт в hex и в печатном виде;
- определённый контейнер и, для ZIP, список элементов с размерами;
- энтропию первых 64 КБ — сразу видно, сжатые это данные или читаемая структура;
- сколько строк нашлось в UTF-8 и в UTF-16-LE (это отвечает на вопрос о
  кодировке, а не гадает о ней);
- сколько встретилось таймкодов `00:00:00:00` и путей вида `C:\…`;
- какие структурные маркеры присутствуют (`Timeline`, `MediaPool`, `ReelName`,
  `Fusion`, …);
- до 25 самых информативных строк-образцов.

Отчёт содержит реальные пути и имена файлов из проектов. Если это нежелательно —
`--redact` заменит содержимое строк на их форму (длина и состав символов).

## Что нужно для версии 2.0

Минимально:

1. Отчёт `rps-probe` по 5–10 проектам разного типа (монтаж, клип, подкаст).
2. Один небольшой `.drp` целиком — тестовый проект из пары клипов на одном
   таймлайне.
3. Знание, что в этом тестовом проекте лежит: имя клипа, таймлайн, дорожка,
   таймкод. Это даёт ожидаемый результат, по которому проверяется парсер.

С этим можно написать разбор структуры и тесты к нему. Без этого — только
догадки, которые сломаются на первом же чужом проекте.
